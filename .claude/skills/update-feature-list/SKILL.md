หน้าที่ของ skill นี้คือ orchestrate การตรวจสอบ backlog → สร้าง/อัปเดต Feature List → สร้าง/อัปเดต User Journey ที่เกี่ยวข้อง โดยมอบหมายงานเขียนไฟล์ให้ subagent เฉพาะทาง 2 ตัว (`feature-list-writer` และ `user-journey-writer`) เป็นคนจัดการ คุณ (main loop) เป็นคนคุยกับผู้ใช้และตัดสิน flow — subagent ไม่คุยกับผู้ใช้โดยตรง

## ขั้นตอน

### 1. รับขอบเขตงาน

ถ้าผู้ใช้ระบุ requirement/หัวข้อเฉพาะที่ต้องการโฟกัส (เช่น "อัปเดต feature list จาก requirement เรื่อง PDPA") ให้ใช้ขอบเขตนั้น ถ้าไม่ระบุ ให้ถือว่าต้องการสแกนทั้ง `docs/01-requirements/backlog.md`

### 2. เรียก subagent `feature-list-writer`

เรียก **Agent tool** โดยระบุ `subagent_type: "feature-list-writer"` และส่งข้อมูลต่อไปนี้:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- ขอบเขตงานจากข้อ 1
- คำตอบจากผู้ใช้ (ถ้ามีจากรอบก่อนหน้า กรณีเคยถูกถามเรื่อง MoSCoW ที่ก้ำกึ่ง)

รอผลลัพธ์ ซึ่งควรมี: ไฟล์ที่สร้าง/แก้ไข, สรุปจำนวน feature ต่อ MoSCoW, รายการที่ backlog/spec ไม่สอดคล้องกัน (ถ้ามี), รายการ `(รอยืนยัน)` พร้อมทางเลือก, และรายชื่อ feature ที่ควรมี/อัปเดต User Journey

### 3. ถ้า feature-list-writer มีรายการที่ต้องยืนยัน

ถ้า subagent รายงานรายการ MoSCoW ที่ก้ำกึ่งหรือความไม่สอดคล้องของ backlog ที่ต้องผู้ใช้ตัดสินใจ ให้ใช้ `AskUserQuestion` ถามผู้ใช้ทีละรายการ **โดยทุกคำถามต้องมีตัวเลือกแนวทางให้เลือกอย่างน้อย 3 ข้อเสมอ** (ใช้ทางเลือกที่ subagent เสนอมาเป็นฐาน) จากนั้นเรียก Agent tool ไปหา `feature-list-writer` อีกครั้งพร้อมคำตอบ เพื่อให้ปรับ feature-list.md ให้ตรงกับคำตอบสุดท้าย

### 4. คัดเลือก flow ที่ต้องทำ User Journey

จากรายชื่อ feature ที่ `feature-list-writer` แนะนำว่าเป็น user-facing flow ในข้อ 2 ให้พิจารณาว่า:

- Feature ไหนควรรวมอยู่ใน journey เดียวกัน (เช่น หลาย feature ที่เป็นขั้นตอนต่อเนื่องของ flow เดียวกัน เช่น "สแกน QR" + "เลือกเมนู" + "ชำระเงิน" + "ออเดอร์เข้าครัว" ควรเป็น journey เดียว ไม่ใช่แยกกัน 4 journey)
- Feature ที่เป็นงานเบื้องหลังล้วนๆ ไม่มี actor ที่เป็นมนุษย์ทำ interaction เป็นขั้นเป็นตอน (เช่น retention policy ลบ log อัตโนมัติ) → ไม่จำเป็นต้องมี User Journey

ถ้าไม่แน่ใจว่าควรจัดกลุ่ม feature เป็น journey อย่างไร ให้ใช้ `AskUserQuestion` เสนอทางเลือกการจัดกลุ่มอย่างน้อย 3 แบบ พร้อมเหตุผลข้อดี/ข้อเสียของแต่ละแบบ ก่อนไปข้อ 5

### 5. เรียก subagent `user-journey-writer` ต่อ 1 flow

สำหรับแต่ละ flow ที่ตัดสินใจแล้ว เรียก **Agent tool** โดยระบุ `subagent_type: "user-journey-writer"` และส่งข้อมูลต่อไปนี้ให้ครบ:

- ชื่อ flow (ภาษาไทย) และ actor หลัก
- ลำดับขั้นตอนของ flow แบบสรุป (ดึงจาก User Story/Business Rules ของ spec ที่เกี่ยวข้อง — อ่าน spec ที่เกี่ยวข้องเองถ้าจำเป็นก่อนสรุปส่งให้ subagent)
- wikilink ของ requirement spec ที่เกี่ยวข้องทั้งหมด
- วันที่ปัจจุบัน
- คำแนะนำเบื้องต้นเรื่องเอกสารใหม่/อัปเดตเอกสารเดิม (ถ้าประเมินได้)

ถ้ามีหลาย flow ที่ต้องทำ ให้เรียกทีละ flow ตามลำดับ (ไม่จำเป็นต้องขนาน เพราะแต่ละ flow จะอัปเดต `docs/02-design/01-prototypes/index.md` ไฟล์เดียวกัน การรันทีละตัวช่วยลดโอกาสชนกัน)

### 6. ถ้า subagent รายงานว่าไม่มั่นใจ

ถ้า `feature-list-writer` หรือ `user-journey-writer` หยุดทำงานและรายงานกลับมาว่าไม่มั่นใจ (พร้อมตัวเลือกที่เสนอมา) ให้นำตัวเลือกเหล่านั้นไปถามผู้ใช้ต่อผ่าน `AskUserQuestion` แล้วเรียก Agent tool ไปหา subagent เดิมอีกครั้งพร้อมคำตอบที่ได้ เพื่อให้ทำงานต่อจนเสร็จ

### 7. สรุปผลให้ผู้ใช้ทราบ

หลังทุก subagent ทำงานเสร็จ ให้สรุปให้ผู้ใช้ทราบ:
- ไฟล์ Feature List ที่สร้าง/แก้ไข พร้อมสรุปจำนวน feature ต่อ MoSCoW
- ไฟล์ User Journey ที่สร้าง/แก้ไขทั้งหมด พร้อม flow ที่ครอบคลุม
- รายการ `(รอยืนยัน)` ที่ยังค้างอยู่ (ถ้ามี หลังผู้ใช้ตอบแล้วควรไม่เหลือ)
- ความไม่สอดคล้องของ backlog/spec ที่พบระหว่างทาง (ถ้ามี) เพื่อให้ผู้ใช้ตามไปแก้ไขเอกสารต้นทาง
