# 002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น

**วันที่สร้าง:** 2026-08-02
**สถานะ:** Draft
**อ้างอิงจาก:** [[20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

## ที่มา / บริบท

ระบบสั่งกาแฟผ่าน QR Code ([[20260802-001-table-ordering-qr|001]]) มีการทำธุรกรรม (ออเดอร์, การชำระเงิน) และมีการจัดการโดยพนักงาน (ยกเลิก/แก้ไขออเดอร์) จึงจำเป็นต้องมี log เพื่อ audit และ troubleshoot เมื่อเกิดปัญหาหรือข้อพิพาท

นอกจากนี้ ระบบอาจมีการเก็บข้อมูลที่ระบุตัวตนลูกค้าได้ในบางกรณี (เช่น ขอใบเสร็จ/ใบกำกับภาษี) จึงต้องปฏิบัติตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) โดยเจ้าของร้านต้องการให้ส่วน PDPA ทำแบบง่ายที่สุดเท่าที่จำเป็น เหมาะสมกับขนาดร้านกาแฟสาขาเดียว ไม่ต้องการกระบวนการที่ซับซ้อนเกินความจำเป็น

## ข้อกำหนด (Requirements)

### Logging (Audit/Transaction Log)

- ระบบต้องบันทึก audit log สำหรับการกระทำสำคัญของพนักงาน/แอดมิน เช่น การยกเลิกออเดอร์, การแก้ไขออเดอร์, การล็อกอินเข้าระบบหลังบ้าน — ต้องระบุว่าใครทำอะไร เมื่อไหร่ (user/role, action, timestamp)
- ระบบต้องบันทึก transaction log สำหรับการชำระเงินและการเปลี่ยนสถานะออเดอร์ (เช่น สั่งซื้อ → ชำระเงินสำเร็จ → ส่งเข้าครัว → เสิร์ฟแล้ว)
- ห้ามบันทึกข้อมูลอ่อนไหวแบบ plain text ลงใน log เด็ดขาด เช่น เลขบัตรเครดิต, รหัสผ่าน, OTP
- จำกัดสิทธิ์การเข้าถึง log เฉพาะเจ้าของร้านและแอดมินเท่านั้น (พนักงานทั่วไปดูไม่ได้)
- เก็บรักษา log ไว้ 90 วัน จากนั้นลบ/ทำลายทิ้งอัตโนมัติ (ตามหลัก data minimization)

### PDPA (แบบง่ายที่สุดเท่าที่จำเป็น)

- ระบบไม่เก็บข้อมูลระบุตัวตนลูกค้า (เบอร์โทร/อีเมล) เป็นค่าเริ่มต้นของการสั่งซื้อทั่วไป
- จะขอเบอร์โทร/อีเมลจากลูกค้า **เฉพาะกรณีที่ลูกค้าต้องการใบเสร็จ/ใบกำกับภาษี** เท่านั้น
- เมื่อขอข้อมูลดังกล่าว ต้องมีข้อความขอความยินยอม (consent) แบบง่าย เช่น checkbox พร้อมข้อความสั้นๆ อธิบายวัตถุประสงค์การใช้ข้อมูล (ออกใบเสร็จ/ใบกำกับภาษีเท่านั้น) ก่อนเก็บข้อมูล
- มี privacy notice แบบสั้น (ไม่ต้องเป็นเอกสารนโยบายฉบับเต็มยาว) แสดงให้ลูกค้าเห็น ณ จุดที่ขอข้อมูล
- ไม่ต้องมีกระบวนการที่ซับซ้อน เช่น ไม่ต้องแต่งตั้งเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO), ไม่ต้องทำระบบสิทธิเจ้าของข้อมูลแบบเต็มรูปแบบ (เช่น portal สำหรับขอเข้าถึง/ลบข้อมูลด้วยตนเอง) — ให้ลูกค้าติดต่อร้านโดยตรงหากต้องการใช้สิทธิ์เหล่านี้ก็เพียงพอ
- ข้อมูลเบอร์โทร/อีเมลที่เก็บไว้ (สำหรับใบเสร็จ) อยู่ภายใต้ retention/การจัดการเช่นเดียวกับ log อื่นๆ ของระบบ (พิจารณาให้สอดคล้องกับหลัก data minimization)

## User Story / Use Case

- ในฐานะเจ้าของร้าน ฉันต้องการดู log การทำงานของพนักงานและธุรกรรม เพื่อตรวจสอบเมื่อเกิดปัญหาหรือข้อพิพาท
- ในฐานะลูกค้าที่ต้องการใบกำกับภาษี ฉันต้องการให้ระบบขอข้อมูลติดต่อของฉันพร้อมอธิบายว่าจะใช้ทำอะไร ก่อนที่ฉันจะยินยอมให้ข้อมูล
- ในฐานะเจ้าของร้าน ฉันต้องการให้ระบบไม่เก็บข้อมูลที่ไม่จำเป็น และไม่ต้องทำกระบวนการ PDPA ที่ซับซ้อนเกินความจำเป็นของร้านขนาดเล็ก

## กฎทางธุรกิจ (Business Rules)

- Log ทุกประเภท (audit log, transaction log) เก็บรักษาไว้สูงสุด 90 วัน แล้วต้องลบ/ทำลายทิ้งอัตโนมัติ
- เฉพาะบัญชีที่มีสิทธิ์ "เจ้าของร้าน" หรือ "แอดมิน" เท่านั้นที่เข้าถึง log ได้ พนักงานทั่วไปไม่มีสิทธิ์เข้าถึง
- ห้ามบันทึกข้อมูลอ่อนไหว (เลขบัตรเครดิต, รหัสผ่าน, OTP) ลงใน log ไม่ว่ากรณีใด
- การเก็บเบอร์โทร/อีเมลของลูกค้าเกิดขึ้นได้เฉพาะเมื่อลูกค้าร้องขอใบเสร็จ/ใบกำกับภาษี และให้ความยินยอมแล้วเท่านั้น
- ข้อมูลติดต่อลูกค้าที่เก็บไว้เพื่อออกใบเสร็จ/ใบกำกับภาษี อยู่ภายใต้ retention policy เดียวกับ log อื่น (90 วัน)

## ขอบเขต (Scope)

### อยู่ในขอบเขต (In scope)
- Audit log สำหรับการกระทำของพนักงาน/แอดมิน (ยกเลิก/แก้ไขออเดอร์, ล็อกอินหลังบ้าน)
- Transaction log สำหรับการชำระเงินและสถานะออเดอร์
- การจำกัดสิทธิ์การเข้าถึง log เฉพาะเจ้าของร้าน/แอดมิน
- Retention policy ของ log (เก็บ 90 วันแล้วลบอัตโนมัติ)
- Consent แบบง่าย (checkbox) สำหรับกรณีขอใบเสร็จ/ใบกำกับภาษี
- Privacy notice แบบสั้น ณ จุดที่ขอข้อมูลลูกค้า

### ไม่อยู่ในขอบเขต (Out of scope)
- การแต่งตั้งเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO)
- ระบบจัดการสิทธิ์เจ้าของข้อมูลแบบเต็มรูปแบบ (self-service portal สำหรับขอเข้าถึง/ลบข้อมูล)
- การเก็บข้อมูลลูกค้าเพื่อการตลาด/CRM
- ระบบ SIEM หรือ log analytics ขั้นสูง
- การรับรอง/ตรวจสอบมาตรฐานความปลอดภัยภายนอก (เช่น ISO 27001)
