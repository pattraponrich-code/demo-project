## รายละเอียดฟีเจอร์

### F-001 - สั่งเมนูผ่านหน้าเว็บด้วยการสแกน QR Code ที่โต๊ะ

- **MoSCoW:** Must — เป็นจุดเริ่มต้นของ flow หลักทั้งหมด ถ้าไม่มีฟีเจอร์นี้ระบบทั้งระบบใช้งานไม่ได้เลย
- **คำอธิบาย:** ลูกค้าสแกน QR Code ที่ติดอยู่บนโต๊ะ เพื่อเปิดหน้าเว็บสั่งเครื่องดื่มโดยไม่ต้องติดตั้งแอพ จากนั้นเลือกเมนู ใส่ตะกร้า และยืนยันคำสั่งซื้อได้จากหน้าเว็บโดยตรง
- **อ้างอิงจาก:** [[../01-spec/20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

### F-002 - ชำระเงินออนไลน์ทันทีก่อนออเดอร์เข้าครัว

- **MoSCoW:** Must — spec ระบุชัดว่า "ระบบต้องรองรับการชำระเงิน 2 รูปแบบ" โดยให้ลูกค้าเลือกได้เอง จึงถือเป็นข้อบังคับหลักของระบบ ไม่ใช่ทางเลือกเสริม
- **คำอธิบาย:** ลูกค้าจ่ายเงินทันทีผ่านระบบออนไลน์ (พร้อมเพย์ / บัตร / e-wallet) ก่อนออเดอร์จะถูกส่งเข้าคิวของบาร์ ตามกฎ "ออเดอร์ที่เลือกจ่ายทันทีจะเข้าคิวบาร์ก็ต่อเมื่อชำระเงินสำเร็จแล้วเท่านั้น"
- **อ้างอิงจาก:** [[../01-spec/20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

### F-003 - สั่งก่อน จ่ายเงินที่เคาน์เตอร์ภายหลัง

- **MoSCoW:** Must — เป็นอีกหนึ่งในสองรูปแบบการชำระเงินที่ spec ระบุว่าระบบต้องรองรับ
- **คำอธิบาย:** ลูกค้าเลือกสั่งซื้อโดยยังไม่จ่ายเงินทันที ออเดอร์จะถูกส่งเข้าคิวของบาร์ทันทีที่ยืนยันคำสั่งซื้อ โดยไม่ต้องรอการชำระเงิน แล้วลูกค้าไปจ่ายที่เคาน์เตอร์ภายหลัง
- **อ้างอิงจาก:** [[../01-spec/20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

### F-004 - แจ้งเตือนออเดอร์ใหม่แบบเรียลไทม์ให้บาร์/ครัว

- **MoSCoW:** Must — ถ้าไม่มีฟีเจอร์นี้ ออเดอร์ที่ลูกค้าสั่งจะไม่ถูกส่งต่อให้บาริสต้ารับรู้เลย ทำให้ flow หลักขาดตอน
- **คำอธิบาย:** เมื่อลูกค้ายืนยันคำสั่งซื้อ (และชำระเงินสำเร็จในกรณีจ่ายทันที) ออเดอร์ต้องถูกส่งแจ้งเตือนไปยังจอ/หน้าจอแสดงรายการออเดอร์ใหม่ที่บาร์/ครัวแบบเรียลไทม์ ให้บาริสต้าเห็นและรับไปทำ
- **อ้างอิงจาก:** [[../01-spec/20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

### F-005 - ระบุหมายเลข/ตำแหน่งโต๊ะกำกับในแต่ละออเดอร์

- **MoSCoW:** Must — spec ระบุชัดว่า "ระบบต้องระบุหมายเลข/ตำแหน่งโต๊ะกำกับไว้ในแต่ละออเดอร์" เพื่อให้พนักงานเสิร์ฟถูกโต๊ะ ถือเป็นข้อกำหนดบังคับ
- **คำอธิบาย:** แต่ละ QR Code ผูกกับหมายเลขโต๊ะที่แน่นอนหนึ่งโต๊ะ และออเดอร์ที่เข้าคิวบาร์ต้องแสดงหมายเลข/ตำแหน่งโต๊ะกำกับไว้เสมอ เพื่อให้พนักงานเสิร์ฟเครื่องดื่มได้ถูกโต๊ะ
- **อ้างอิงจาก:** [[../01-spec/20260802-001-table-ordering-qr|001 - ระบบสั่งกาแฟที่โต๊ะผ่าน QR Code]]

### F-006 - Audit log การกระทำของพนักงาน/แอดมิน

- **MoSCoW:** Must — spec ระบุว่า "ระบบต้องบันทึก audit log" สำหรับการกระทำสำคัญของพนักงาน/แอดมิน
- **คำอธิบาย:** บันทึก audit log สำหรับการกระทำสำคัญของพนักงาน/แอดมิน เช่น การยกเลิกออเดอร์, การแก้ไขออเดอร์, การล็อกอินเข้าระบบหลังบ้าน โดยระบุว่าใครทำอะไร เมื่อไหร่ (user/role, action, timestamp) เพื่อ audit และ troubleshoot เมื่อเกิดปัญหาหรือข้อพิพาท
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]

### F-007 - Transaction log การชำระเงินและสถานะออเดอร์

- **MoSCoW:** Must — spec ระบุว่า "ระบบต้องบันทึก transaction log" สำหรับการชำระเงินและการเปลี่ยนสถานะออเดอร์
- **คำอธิบาย:** บันทึก transaction log สำหรับการชำระเงินและการเปลี่ยนสถานะออเดอร์ (เช่น สั่งซื้อ → ชำระเงินสำเร็จ → ส่งเข้าครัว → เสิร์ฟแล้ว) เพื่อใช้ตรวจสอบเมื่อเกิดปัญหาหรือข้อพิพาท
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]

### F-008 - จำกัดสิทธิ์การเข้าถึง log เฉพาะเจ้าของร้าน/แอดมิน

- **MoSCoW:** Must — เป็น business rule บังคับของ spec ("เฉพาะบัญชีที่มีสิทธิ์เจ้าของร้านหรือแอดมินเท่านั้นที่เข้าถึง log ได้")
- **คำอธิบาย:** จำกัดสิทธิ์การเข้าถึง log (audit log, transaction log) ให้เฉพาะเจ้าของร้านและแอดมินเท่านั้น พนักงานทั่วไปดูไม่ได้
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]

### F-009 - Retention policy: เก็บ log 90 วันแล้วลบอัตโนมัติ

- **MoSCoW:** Must — เป็น business rule บังคับตามหลัก data minimization ที่ spec ระบุไว้ชัดเจน (เก็บสูงสุด 90 วันแล้วต้องลบ/ทำลายทิ้งอัตโนมัติ) ครอบคลุมทั้ง log ของระบบ และข้อมูลติดต่อลูกค้าที่เก็บไว้เพื่อออกใบเสร็จ/ใบกำกับภาษี (retention เดียวกัน)
- **คำอธิบาย:** เก็บรักษา log (และข้อมูลติดต่อลูกค้าที่เก็บเพื่อใบเสร็จ/ใบกำกับภาษี) ไว้สูงสุด 90 วัน จากนั้นลบ/ทำลายทิ้งอัตโนมัติตามหลัก data minimization
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]

### F-010 - ป้องกันข้อมูลอ่อนไหวไม่ให้ถูกบันทึกลง log แบบ plain text

- **MoSCoW:** Must — spec ระบุว่า "ห้ามบันทึกข้อมูลอ่อนไหวแบบ plain text ลงใน log เด็ดขาด" ไม่มีเงื่อนไขผ่อนปรน
- **คำอธิบาย:** ห้ามบันทึกข้อมูลอ่อนไหว เช่น เลขบัตรเครดิต, รหัสผ่าน, OTP ลงใน log แบบ plain text ไม่ว่ากรณีใด เป็นมาตรการความปลอดภัยพื้นฐานที่ต้องมีคู่กับทุกฟีเจอร์ที่เขียน log (F-006, F-007)
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]

### F-011 - ขอ consent + privacy notice แบบสั้น เมื่อลูกค้าขอใบเสร็จ/ใบกำกับภาษี

- **MoSCoW:** Must — spec ระบุว่าการขอเบอร์โทร/อีเมล "ต้องมีข้อความขอความยินยอม (consent)" และ "ต้องมี privacy notice แบบสั้น" ก่อนเก็บข้อมูลเสมอ ถือเป็นข้อบังคับตาม PDPA ไม่ใช่ทางเลือก
- **คำอธิบาย:** ระบบไม่เก็บข้อมูลระบุตัวตนลูกค้า (เบอร์โทร/อีเมล) เป็นค่าเริ่มต้น จะขอข้อมูลนี้เฉพาะกรณีลูกค้าต้องการใบเสร็จ/ใบกำกับภาษีเท่านั้น โดยต้องแสดง privacy notice แบบสั้นและให้ลูกค้ายืนยันความยินยอม (เช่น checkbox) ก่อนเก็บข้อมูลทุกครั้ง
- **อ้างอิงจาก:** [[../01-spec/20260802-002-system-log-pdpa|002 - การเก็บ Log ของระบบ และการปฏิบัติตาม PDPA เบื้องต้น]]
